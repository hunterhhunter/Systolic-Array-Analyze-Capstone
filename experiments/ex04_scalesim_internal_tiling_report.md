# SCALE-Sim Internal Tiling/Folding Report

## Summary

SCALE-Sim does perform an internal tiling-like step, but the code calls it
**folding** rather than compiler-level tiling. A topology CSV row is treated as
one layer. Inside that layer, SCALE-Sim maps the layer's transformed GEMM-like
operand matrices onto the fixed systolic array dimensions and splits the work
into row/column folds whenever the operand dimensions exceed the array.

This is different from the IREE Transform Dialect tiling used in this project:

- IREE tiling creates many explicit topology rows, one row per compiler tile.
- SCALE-Sim folding happens inside each topology row, according to array size
  and dataflow.
- The standard reports do not expose `row_fold` or `col_fold` directly.
  Their effects appear indirectly in cycles, mapping efficiency, compute
  utilization, SRAM/DRAM accesses, and trace lengths.

## Code Path

The relevant execution path is:

```text
topology CSV row
  -> topology_utils.py
     computes Conv/GEMM hyperparameters and dataflow-specific dimensions
  -> operand_matrix.py
     builds IFMAP / Filter / OFMAP operand matrices
  -> systolic_compute_{ws,os,is}.py
     splits operand matrices into folds based on array dimensions
  -> double_buffered_scratchpad_mem.py
     simulates SRAM/DRAM service for the generated demand matrices
  -> COMPUTE_REPORT.csv / BANDWIDTH_REPORT.csv / DETAILED_ACCESS_REPORT.csv
```

For the current WS experiments, the main implementation is
`SCALE-Sim/scalesim/compute/systolic_compute_ws.py`.

## What SCALE-Sim Folds

For Conv input, SCALE-Sim first derives an equivalent GEMM shape:

```text
M = number of output pixels
N = number of filters
K = filter_h * filter_w * channels
```

Then, for each dataflow, it maps those dimensions into spatio-temporal
parameters:

```text
WS: S_r = K, S_c = N, T = M
OS: S_r = M, S_c = N, T = K
IS: S_r = K, S_c = M, T = N
```

For WS, with array dimensions `(ArrayHeight, ArrayWidth)`, SCALE-Sim computes:

```text
row_fold = ceil(S_r / ArrayHeight)
col_fold = ceil(S_c / ArrayWidth)
```

In the current MatMul-as-GEMM topology, `S_r = K` and `S_c = N`. Therefore a
topology row `M=8, N=8, K=8` on an `8x8` WS array has:

```text
row_fold = ceil(8 / 8) = 1
col_fold = ceil(8 / 8) = 1
```

So each explicit IREE tile fits the SCALE-Sim array without additional
spatial folding. The measured overhead in the walking skeleton is mostly from
prefetch and systolic fill/drain behavior, not from extra internal folds.

For TinyConv, the equivalent GEMM shape is:

```text
M = H_out * W_out = 4
N = NumFilter = 2
K = Channels * FilterH * FilterW = 12
```

On a `3x3` WS array:

```text
row_fold = ceil(12 / 3) = 4
col_fold = ceil(2 / 3) = 1
```

This explains why even a single Conv topology row can produce multiple internal
compute folds inside SCALE-Sim.

## How It Appears In Reports

SCALE-Sim's public CSV reports do not include explicit fold counters. Instead:

- `COMPUTE_REPORT.csv`
  - `Total Cycles` reflects compute demand after internal folding and pipeline
    fill/drain.
  - `Mapping Efficiency %` averages PE occupancy across folds.
  - `Compute Util %` additionally reflects pipeline timing losses.
- `DETAILED_ACCESS_REPORT.csv`
  - SRAM/DRAM start/stop cycles expose prefetch windows and memory-service
    timing.
  - Negative DRAM start cycles indicate prefetch before compute begins.
- `layer*/{IFMAP,FILTER,OFMAP}_{SRAM,DRAM}_TRACE.csv`
  - These are the most direct evidence of internal folding because they contain
    the full demand trace after SCALE-Sim has concatenated fold demand matrices.

Current anchors:

```text
TinyConv:
  COMPUTE_REPORT: total incl. prefetch = 99, compute = 31
  DETAILED_ACCESS: IFMAP/FILTER DRAM start = -66
  Interpretation: one Conv row expands into multiple internal WS folds and a
  large prefetch window.

Walking skeleton 8x8x8:
  Each topology row: total incl. prefetch = 102, compute = 29
  IREE creates 128 explicit topology rows.
  Interpretation: compiler tiling dominates row count; SCALE-Sim internal fold
  count per row is 1x1 for the 8x8x8 tile on an 8x8 WS array.
```

## Implication For This Project

The project currently has two levels of decomposition:

1. **Compiler/IREE tiling**
   - Explicitly creates topology rows.
   - This is the experimental variable we control: tile size.

2. **SCALE-Sim internal folding**
   - Happens inside each topology row.
   - Controlled by array size, dataflow, and topology dimensions.
   - Should be treated as SCALE-Sim's mapping model, not as the compiler's tile
     schedule.

For clean experiments, we should report both:

```text
compiler_tiles = number of topology rows generated by mlir2scalesim
estimated_internal_folds = ceil(S_r / ArrayHeight) * ceil(S_c / ArrayWidth)
```

This prevents a misleading interpretation where all cycle changes are
attributed to IREE tile size. Some changes may come from whether each explicit
tile fits the SCALE-Sim array cleanly or requires internal folding.

## Recommended Next Step

Add an analysis helper that computes estimated internal folds from topology CSV
and architecture config without modifying SCALE-Sim:

```text
input:
  topology row
  dataflow
  ArrayHeight, ArrayWidth

output:
  M, N, K
  S_r, S_c, T
  row_fold, col_fold, total_internal_folds
```

Then include these fields in `results/results.parquet` for Phase 4+ sweeps.
This is lightweight, reproducible, and enough for reporting. Directly modifying
SCALE-Sim to print fold counters is optional and can wait until the analysis
requires deeper trace-level validation.
